# Cross-genre video asset library

This is the shared asset pool for future videos, not a collection dedicated to the self-improvement channel. It separates three classes so later projects can reuse resources without guessing at rights:

1. **Bundled / redistributable** — original assets generated by this repository and source packs whose public page explicitly identifies the pack as CC0. Each downloaded item gets a provenance record and SHA-256.
2. **Use-in-video, source-only** — free stock footage, music, and other media whose terms allow incorporation into a finished film but prohibit redistributing the raw files as a standalone pack. The source URL and restrictions live in the catalog; the builder does not download these into our release ZIP.
3. **Review required** — anything with a non-CC0 license, unclear provenance, people/brand restrictions, or license metadata that cannot be confirmed. Do not bundle automatically.

## New source and rights rules

- **Smithsonian:** only images that are explicitly CC0 both at the collection record and at the selected media object are bundled. The API may require a registered key for reliable usage; API failures are recorded, not represented as zero uncertainty.
- **Rijksmuseum:** only item-level CC0/Public Domain Mark images are bundled. Source record, creator, exact rights statement and IIIF image URL stay in the manifest. Other rights, including culturally sensitive context or trademarks, must still be reviewed.
- USGS and NOAA are documented as future source lanes, not claimed as downloaded automatically; their official guidance says public-domain status can have item-level exceptions and credit/endorsement rules.

- NASA media is tracked under NASA’s own media-use guidance and **must not** be labelled CC0. Keep NASA attribution, never imply NASA endorsement, avoid logos/seals, and check identifiable-person/privacy/publicity constraints.
- Library of Congress photos are auto-bundled only if the item-level rights statement is explicitly positive and non-conflicting. The user remains responsible for context and other rights.
- The Met and Wikimedia continue to use per-item Public Domain/CC0 checks. Smithsonian Open Access is attempted with the configured `SMITHSONIAN_API_KEY` or the low-volume `DEMO_KEY` fallback; no Smithsonian asset is counted as successful unless both the record and exact media file pass the CC0 gate.
- Exact successful download counts are generated into each `ASSET_INDEX.json`; API timeouts and skipped records are not represented as successful downloads.

## Usage

Use `GENRE_PLAYBOOK.md` to select a visual language first, then search by category and combine only assets that help the story. Do not make every film look alike by swapping the title over the same background. Mix source media, purpose-built environments, real 3D models, diagrams, and custom composition when the genre calls for them.

The download workflow is intentionally rate-limited and size-capped. A partial third-party failure should show in the index; it must never be reported as a complete pack unless checksums and counts confirm it.

## Build 44: OpenGameArt item-level CC0 library

This source lane uses OpenGameArt's official advanced-search CC0 filter to discover five different families: 2D sprites and tiles, 3D models, textures, sound effects, and music. A search filter is not treated as a license grant: every candidate's own item page must have exactly one CC0 1.0 entry in its License(s) field. Items with CC-BY, CC-BY-SA, GPL, mixed, missing or ambiguous license fields are skipped.

The downloader accepts attachments only from the official HTTPS `opengameart.org/sites/default/files/` host path, checks the actual media file signatures, validates ZIP integrity, extracts through the existing safe archive allow-list, and records creator, item URL, direct attachment URL, CC0 basis, archive digest and per-file SHA-256. SVG and native Blender project files are excluded from these third-party archives to avoid bundling active content. The current search ceilings are 6 2D packs, 6 3D packs, 5 texture packs, 5 SFX packs and 5 music packs; these are ceilings, not promised downloads. The generated report is authoritative.

Official source: [OpenGameArt advanced search](https://opengameart.org/art-search-advanced) and [site FAQ](https://opengameart.org/content/faq).

## Build 44: curated Google Fonts with verified OFL licenses

The typography source lane selects up to 20 curated family directories from the official `google/fonts` repository. Each family's own `OFL.txt` is downloaded and inspected before any font binary is accepted. Only families carrying the SIL Open Font License Version 1.1 marker and a copyright statement proceed. At most two TTF faces are retained per family, each with a TrueType/OpenType sfnt signature check and SHA-256; the exact family `OFL.txt`, its checksum, raw font URL and family page are kept alongside the font. The aggregate font-download ceiling is 90 MiB. These files remain under their individual SIL OFL 1.1 terms rather than being relabelled CC0.

Official repository: [Google Fonts](https://github.com/google/fonts). License: [SIL Open Font License](https://openfontlicense.org/).

## Build 45: multi-volume release packaging

The library is no longer tied to a single ZIP. The packager estimates the raw resource size:

- Compact builds keep the familiar `video-asset-library.zip` for one-click extraction.
- Larger builds create a small `video-assets-catalog.zip` plus independently downloadable family volumes for original graphics, photography, footage, audio, 3D/models, textures and typography.
- Each resource volume targets at most 1.7 GB uncompressed; each uploaded release asset is checked against a 1.9 GB ceiling, below GitHub's documented 2 GiB per-asset limit.
- `ASSET_BUNDLES.json` records every volume, SHA-256, byte count, file count and the exact paths it contains. The workflow verifies all ZIPs and confirms every library file is included exactly once.

For a multi-volume release, download the catalog bundle and the resource families you need, then extract all selected ZIPs into the same parent folder. Keep the `video-asset-library/` paths intact. This is the foundation for growing toward tens of gigabytes without one unmanageable archive.
